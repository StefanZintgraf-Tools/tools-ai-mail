# Use Case: Commit Approved Filings

## Overview
**Use Case ID:** UC-003
**Use Case Name:** Commit Approved Filings
**Primary Actor:** User
**Goal:** Run `apply` so each approved Attachment is copied into its Target Location under its Target Filename, with provenance recorded and identical content de-duplicated, so only approved rows are committed.
**Status:** Draft
**Requirements covered:** FR-008, FR-009, FR-012

## Preconditions
- A decided Action Plan exists (UC-002) with one or more approved Proposals.
- The Provenance Ledger is reachable at its owner-private, non-synced location.
- No other pipeline run is writing the Provenance Ledger or the Staging Area (single-writer).

## Main Success Scenario
1. The User runs `apply` against the decided Action Plan.
2. For each approved Proposal, the system computes (or reuses) the Attachment's content-hash and checks the Provenance Ledger's dedup decision (keyed on content-hash only).
3. If the content is new, the system copies the Attachment into its Target Location under its Target Filename.
4. The system stamps the filed copy with the Provenance back-link (Message-ID, Mail date, Sender).
5. The system appends a provenance link to the Provenance Ledger, keyed on `(Message-ID, content-hash)`, recording the filed-copy location.
6. The system records the Attachment's terminal outcome as **filed** and updates the per-run outcome tally.
7. The system reports the commit results to the User.

## Alternative Flows
### A1: Identical content already filed (dedup)
**Trigger:** Step 2 — the content-hash already exists in the Provenance Ledger.
**Flow:** The system does **not** write a second copy. It appends only a new provenance link for the source Mail, so a re-sent or re-scanned Attachment is traceable without duplication. Resume at step 6 (outcome: filed, via existing copy).

### A2: Non-approved rows
**Trigger:** Step 1 — the Action Plan contains rejected or undecided Proposals.
**Flow:** The system skips them entirely; only approved rows are committed. Continue with the approved rows.

### A3: Edited Target Filename or Target Location
**Trigger:** Step 3 — the User edited the name or destination in UC-002.
**Flow:** The system writes under the edited Target Filename into the edited Target Location. Resume at step 4.

### A4: Same-path / different-content collision at commit
**Trigger:** Step 3 — the Target Location + Target Filename now holds different bytes.
**Flow:** The system applies the deterministic mail-date prefix once; if the prefixed path also holds different bytes, it declares a Conflict, routes the Attachment to the Staging Area, records the outcome as **conflicted**, and does not overwrite. Resume at step 6 for remaining rows.

### A5: Copy fails (errored)
**Trigger:** Step 3 — the copy cannot be written.
**Flow:** The system routes the Attachment to the Staging Area as an **errored** outcome and surfaces it; it is never silently dropped. Resume at step 6 for remaining rows.

## Postconditions
### Success Postconditions
- Every approved, non-duplicate Attachment exists as a copy in its Target Location under its Target Filename.
- Each filed copy carries its Provenance back-link, and the Provenance Ledger has an append record `(Message-ID, content-hash) → filed-copy location` for it.
- No second copy exists for any content-hash already in the ledger; the source Mail and Attachment are unchanged.

### Failure Postconditions
- An Attachment that could not be committed lands in the Staging Area as conflicted or errored and appears in the Action Plan; no partial or overwriting write is left behind.

## Business Rules
### BR-001: Commit only approved rows by copy
`apply` copies only Proposals carrying an approve decision, and copies only — never moving, deleting, or modifying the source — enforces the PROPOSAL "copied only after approve; commit copies only" invariant (entity_model PROPOSAL) and C-002 / C-001 / FR-008.

### BR-002: Dedup keys on content-hash only
The decision to write a file at all keys on content-hash alone; a missing or reused Message-ID can never cause a duplicate file, and identical content yields only a new provenance link — enforces the PROVENANCE_LEDGER dedup-key invariant (entity_model PROVENANCE_LEDGER) and NFR-002 / C-010 / FR-012.

### BR-003: Provenance link recorded at commit
Every filed copy gets a Provenance back-link on the copy and an append record `(Message-ID, content-hash) → location` in the Provenance Ledger — enforces the PROVENANCE_LEDGER provenance-link invariant (entity_model PROVENANCE_LEDGER) and FR-009.

### BR-004: Append-only ledger
The Provenance Ledger is appended to, never purged or rewritten in v1 — enforces the PROVENANCE_LEDGER append-only invariant (entity_model PROVENANCE_LEDGER) and C-013.

### BR-005: No write-back to the mailbox
Provenance is served by the external ledger and the on-copy back-link; the source Mail is never annotated — enforces the PROVENANCE_LEDGER "no write-back" invariant (entity_model PROVENANCE_LEDGER) and C-001 / C-008.

### BR-006: Credential containment at commit
No mail-access credential may be written into the Provenance Ledger, the back-link, or logs during commit — enforces the PROVENANCE_LEDGER credential boundary (entity_model PROVENANCE_LEDGER) and NFR-006 / C-011 / ADR-0005.

### BR-007: Conflict, never overwrite
A surviving same-path/different-content collision routes to the Staging Area as a Conflict and is never auto-overwritten — enforces the CONFLICT invariant (entity_model CONFLICT) and C-010.
