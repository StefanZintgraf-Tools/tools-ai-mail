# Use Case: Generate Filing Proposals for a Run

## Overview

**Use Case ID:** UC-001
**Use Case Name:** Generate Filing Proposals for a Run
**Primary Actor:** User
**Goal:** Produce an Action Plan of filing Proposals for a chosen set of Mails, so the User does not have to scan the inbox or decide each file's destination manually.
**Status:** Draft
**Requirements covered:** FR-014, FR-001, FR-002, FR-004, FR-005, FR-013

## Preconditions

- The User has declared exactly one Routing Root (M2 v1 supports a single root — C-016).
- The mail-access method is configured, and its credentials are available from the OS-level secret store (read at run time, never from any M2 artifact).
- No other pipeline run is writing the Provenance Ledger or the Staging Area — M2 v1 assumes a single writer.

## Main Success Scenario

1. The User starts a run, specifying the Run Scope as a source folder and an optional date range.
2. The system reads the mail-access credentials at run time from the OS-level secret store.
3. The system enumerates the Mails in the Run Scope.
4. For each Mail, the system detects every Attachment worth filing, surfacing ambiguous Attachments (e.g. generic names like `scan.jpg`) rather than dropping them.
5. The system extracts the file object of each detected Attachment.
6. The system computes the content-hash of each extracted Attachment.
7. The system derives the Routing Key — the Sender (From email address) — and maps it to an existing Target Location beneath the Routing Root, producing a location-confidence.
8. The system forms one Proposal per Attachment, carrying Source Mail, Subject Attachment (content-hash), Routing Key, Target Location, Target Filename (defaulting to the original Attachment name), and Confidence.
9. The system serializes all Proposals of the run into an Action Plan, including the per-run outcome tally (counts of filed / staged / conflicted / errored).
10. The system presents the Action Plan to the User for review (continues in UC-002).

## Alternative Flows

### A1: Unrecognized Sender or below-threshold confidence

**Trigger:** Step 7 — the Sender maps to no Target Location, or the location-confidence is below the configured threshold.
**Flow:** The system routes the Proposal to the Staging Area (`_review/`) with no auto-approval, and records the Attachment's terminal outcome as **staged** in the Action Plan. Resume at step 8 for the remaining Attachments.

### A2: Multi-folder sender

**Trigger:** Step 7 — the Sender has historically filed into more than one folder.
**Flow:** The Proposal is below location-confidence by construction; the system routes it to the Staging Area as an accepted miss (the document-type dimension that would disambiguate it is deferred to M2b). Resume at step 8.

### A3: Same-path / different-content collision

**Trigger:** Step 8 — the proposed Target Location + Target Filename already holds different bytes.
**Flow:** The system applies the deterministic mail-date prefix (`YYYY-MM-DD-<original>`) once as a tiebreaker. If the prefixed path is free or holds identical bytes, the Proposal proceeds. If the prefixed path *also* holds different bytes, the system flags a Conflict and routes the Proposal to the Staging Area, recording the outcome as **conflicted** in the Action Plan. Resume at step 8.

### A4: Attachment cannot be processed (errored)

**Trigger:** Steps 5–7 — an Attachment cannot be hashed, parsed, or extracted.
**Flow:** The system routes the Attachment to the Staging Area as an explicit **errored** outcome and surfaces it in the Action Plan, even though no routable Proposal could be formed. The Attachment is never silently dropped. Resume at step 8 for the remaining Attachments.

### A5: Re-run over already-processed or already-staged mail

**Trigger:** Step 3 — the Run Scope overlaps Mails or Attachments processed by a previous run.
**Flow:** Re-scanning is safe: dedup keys on content-hash, so previously filed Attachments produce no duplicate write, and a staged-but-unfiled Attachment is re-written to its content-hash-addressed `_review/` path (overwriting identical bytes harmlessly) and re-proposed in the new Action Plan until the User drains `_review/`. Continue normally.

## Postconditions

### Success Postconditions

- An Action Plan exists for the run, in which **every** Attachment the run began processing has exactly one terminal outcome (filed-candidate / staged / conflicted / errored) and the four-outcome tally sums to 100% of the Attachments processed.
- No Attachment has been written to any Target Location — only Proposals have been produced.
- The source Mails and Attachments are unchanged; nothing was written back to the mailbox.

### Failure Postconditions

- If the run cannot start (no Routing Root, missing credentials, or another run in progress), no Action Plan is produced and no Target Location or Staging Area is written.

## Business Rules

### BR-001: Inclusion bias on detection

F01 must surface 100% of ambiguous Attachments for review; 0 may be silently dropped — enforces the ATTACHMENT "no silent drop (terminal outcome)" invariant (entity_model ATTACHMENT) and NFR-004.

### BR-002: No silent drop (terminal outcome)

Every Attachment the run begins processing reaches exactly one terminal outcome — filed / staged / conflicted / errored — and an Attachment that cannot be hashed, parsed, or copied routes to the Staging Area as *errored* — enforces the ATTACHMENT terminal-outcome invariant (entity_model ATTACHMENT) and C-014.

### BR-003: Sender-only routing

The Routing Key is the Sender alone in v1; an unrecognized Sender misses the map and routes to the Staging Area — enforces the ROUTING_KEY one-dimensional invariant (entity_model ROUTING_KEY) and ADR-0003.

### BR-004: Existing folders only

A Target Location must be an existing folder beneath a Routing Root and is never fabricated; the Staging Area is not a Target Location — enforces the TARGET_LOCATION invariant (entity_model TARGET_LOCATION) and C-003.

### BR-005: Confidence gate

When the location-confidence is below the configured threshold, the Proposal routes to the Staging Area with 0 auto-approvals below threshold — enforces the PROPOSAL / CONFIDENCE gate invariant (entity_model PROPOSAL, CONFIDENCE) and NFR-001.

### BR-006: Conflict vs dedup

A same-path/different-content collision that survives the one-shot mail-date-prefix tiebreaker is a Conflict routed to the Staging Area, never auto-overwritten; identical content is not a Conflict — enforces the CONFLICT invariant (entity_model CONFLICT) and C-010.

### BR-007: Non-destructive scan

Scanning Mails and extracting Attachments must never move, delete, or modify the source Mail or Attachment — enforces the PROPOSAL "commit copies only" invariant (entity_model PROPOSAL) and C-001.

### BR-008: Credential containment

Mail-access credentials are read at run time from the OS-level secret store and must never be written into the Action Plan or any other M2 artifact — enforces the PROVENANCE_LEDGER credential boundary (entity_model PROVENANCE_LEDGER) and NFR-006 / C-011 / ADR-0005.

### BR-009: Single-writer run

Exactly one run may write the Staging Area and Provenance Ledger at a time; overlapping runs are unsupported in v1 — enforces the PROVENANCE_LEDGER single-writer invariant (entity_model PROVENANCE_LEDGER) and C-015.

### BR-010: Run outcome tally

The Action Plan must carry the per-run tally of filed / staged / conflicted / errored Attachments, and the four counts must sum to 100% of the Attachments the run began processing — enforces the ACTION_PLAN run-outcome-visibility invariant (entity_model ACTION_PLAN) and NFR-008.
