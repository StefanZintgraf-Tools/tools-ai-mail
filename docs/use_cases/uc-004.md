# Use Case: Trace a Filed Copy to/from its Source Mail

## Overview
**Use Case ID:** UC-004
**Use Case Name:** Trace a Filed Copy to/from its Source Mail
**Primary Actor:** User
**Goal:** Locate a filed copy from its source Mail, and the source Mail from a filed copy, so nothing is lost in the filing process even after the User reorganizes the mailbox.
**Status:** Draft
**Requirements covered:** FR-010

## Preconditions
- At least one Attachment has been committed (UC-003), so a Provenance back-link exists on its copy and a provenance link exists in the Provenance Ledger.
- The Provenance Ledger is reachable at its owner-private, non-synced location.

## Main Success Scenario
1. The User has a source Mail and wants to find where its Attachment was filed.
2. The User reads the Mail's Message-ID.
3. The User inspects the Provenance Ledger for records matching that Message-ID (manual inspection of the greppable ledger).
4. The system (ledger) yields the filed-copy location(s) for that Mail.
5. The User opens the filed copy at the reported Target Location.

## Alternative Flows
### A1: Copy → Mail (reverse direction)
**Trigger:** Step 1 — the User starts from a filed copy and wants the originating Mail.
**Flow:** The User reads the Provenance back-link stamped on the copy (Message-ID, Mail date, Sender) and uses the Message-ID to locate the source Mail. The search runs over the Reverse-Search Scope — the inbox (always) plus any folders the User has configured — not the whole mailbox, so reverse resolution stays bounded even when the mailbox holds a large archive. The lookup does not depend on the copy's or the Mail's folder location *within that scope*.

### A2: Source Mail relocated after filing
**Trigger:** Step 3 — the User has since archived or moved the source Mail within the mailbox.
**Flow:** Mail→Copy still succeeds unconditionally — it greps the Provenance Ledger by Message-ID and never touches folder location. Copy→Mail still succeeds **provided the Mail was moved into a folder within the Reverse-Search Scope** (the inbox is always included; the User adds archive folders as needed). A Mail relocated outside the configured scope is not found by the reverse trace in v1. Resume at step 4.

### A3: Message-ID absent on the source Mail
**Trigger:** Step 2 — the Mail carries no Message-ID.
**Flow:** Identity falls back to the synthetic `hash(from + date + subject)`, under which the provenance link was recorded, so the Mail remains addressable. Resume at step 3.

## Postconditions
### Success Postconditions
- The User has resolved the source-Mail ↔ filed-copy relationship in the requested direction.
- No write-back to the mailbox occurred; the Provenance Ledger and back-link are unchanged by the lookup.

### Failure Postconditions
- If no ledger record and no back-link exist for the item, the trace cannot be resolved — but this can only happen for an Attachment that was never committed (it would instead be in the Staging Area).

## Business Rules
### BR-001: Bidirectional findability via provenance
100% of filed copies must be resolvable from both their Target Location and their source Mail — the Provenance Ledger answers Mail→Copy and the on-copy back-link answers Copy→Mail — enforces the PROVENANCE_LEDGER / PROVENANCE_BACK_LINK findability invariant (entity_model PROVENANCE_LEDGER, PROVENANCE_BACK_LINK) and NFR-005 / FR-010.

### BR-002: Location-independent lookup
Both directions key on the portable Message-ID, never on folder location, so the trace survives the User relocating the source Mail — enforces the PROVENANCE_LEDGER "stay resolvable after relocation" invariant (entity_model PROVENANCE_LEDGER) and NFR-005.

### BR-003: Portable mail identity with fallback
The Message-ID is access-method-independent (never an IMAP UID or Graph item-ID); when absent, identity falls back to `hash(from + date + subject)` — enforces the MAIL Message-ID invariant (entity_model MAIL) and ADR-0004.

### BR-004: No write-back; manual resolution in v1
Tracing is served by the external ledger and the back-link without annotating the mailbox, and resolution in either direction is manual ledger inspection (no dedicated lookup tool in v1) — enforces the PROVENANCE_LEDGER "no write-back / manual resolution" invariant (entity_model PROVENANCE_LEDGER) and C-001 / C-008.

### BR-005: Owner-private ledger siting
The Provenance Ledger is PII-bearing and must be sited outside any cloud-synced or shared path — enforces the PROVENANCE_LEDGER PII-siting invariant (entity_model PROVENANCE_LEDGER) and NFR-007 / C-012 / ADR-0001.

### BR-006: Bounded reverse search over a configured folder scope
The Copy→Mail trace searches only the Reverse-Search Scope — the inbox (always) plus folders the User configures — never the whole mailbox, so reverse resolution stays bounded on a large archive. Consequently the relocation guarantee is scoped: a source Mail stays reverse-findable only while it lives within the Reverse-Search Scope (Mail→Copy is unaffected — it greps the ledger). Broader / index-backed reverse search is deferred (method TBD, tied to C-007) — enforces the scoped form of NFR-005 and CONTEXT Reverse-Search Scope.
