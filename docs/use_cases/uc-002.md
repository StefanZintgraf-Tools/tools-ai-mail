# Use Case: Review and Decide on Proposals

## Overview
**Use Case ID:** UC-002
**Use Case Name:** Review and Decide on Proposals
**Primary Actor:** User
**Goal:** Review all proposed filing actions together as an editable Action Plan and approve, edit, or reject each one, so the User stays in control of what gets filed without opening the original mail.
**Status:** Draft
**Requirements covered:** FR-006, FR-007, FR-011

## Preconditions
- An Action Plan has been produced for a run (UC-001) and is available to the User.
- Each Proposal in the plan carries its M2 v1 fields: Sender (via Routing Key), Target Location, location-confidence, and Target Filename.

## Main Success Scenario
1. The system presents the Action Plan to the User as a single editable view, with every Proposal and its full context (Sender, proposed Target Location, location-confidence score, Target Filename), plus the per-run outcome tally.
2. The User reviews each Proposal using only the context shown, without opening the source Mail.
3. For each Proposal, the User records a decision: approve, edit, or reject.
4. The User optionally edits a Proposal — re-targeting it or renaming its Target Filename — before deciding.
5. The User saves the decided Action Plan.

## Alternative Flows
### A1: Edit the Target Filename (manual rename)
**Trigger:** Step 4 — the User wants the filed copy under a different name.
**Flow:** The User edits the Target Filename of the Proposal in the Action Plan to a name of their choice. The edit is treated as an approval-with-change; the commit (UC-003) writes under the edited name. Resume at step 5.

### A2: Re-target a Proposal
**Trigger:** Step 4 — the User wants the copy filed in a different existing folder (e.g. to rescue a staged or mis-routed Proposal).
**Flow:** The User edits the Target Location to another existing folder beneath the Routing Root. Resume at step 5.

### A3: Reject a Proposal
**Trigger:** Step 3 — the User does not want this Attachment filed.
**Flow:** The User marks the Proposal rejected; it will not be committed in UC-003. Resume at step 3 for the remaining Proposals.

### A4: Leave a staged / conflicted / errored item undecided
**Trigger:** Step 3 — a Proposal landed in the Staging Area or as a Conflict/errored outcome.
**Flow:** The User may leave it for `_review/` (M2 never auto-deletes from the Staging Area) or rescue it via A2/A1. Undecided non-approved rows are not committed. Resume at step 3.

## Postconditions
### Success Postconditions
- Each Proposal in the Action Plan carries exactly one recorded decision (approve / edit / reject) or remains explicitly undecided (non-approved).
- Any edits (re-target, rename) are persisted in the Action Plan; no Attachment has yet been written to a Target Location.

### Failure Postconditions
- If the User makes no decisions, every Proposal stays non-approved and UC-003 will commit nothing.

## Business Rules
### BR-001: Proposal completeness before approval
100% of Proposals must display all M2 v1 fields — Sender, Target Location, and location-confidence — before the User decides — enforces the PROPOSAL completeness invariant (entity_model PROPOSAL) and NFR-003.

### BR-002: Human-in-the-loop gate
No Attachment may be committed without an explicit approve decision on its Proposal; the Action Plan is the realization of the require_approval gate — enforces the APPROVAL_REQUEST "approve is the precondition for commit" invariant (entity_model APPROVAL_REQUEST) and C-002 / ADR-0002.

### BR-003: One decision per Proposal per run
Each Proposal carries at most one decision in a given run — enforces the APPROVAL_REQUEST identity invariant (one decision per Gated Proposal per run; entity_model APPROVAL_REQUEST).

### BR-004: Free manual rename
The Target Filename defaults to the original Attachment name and is freely editable by the User in the Action Plan before commit — enforces the TARGET_FILENAME invariant (entity_model TARGET_FILENAME) and FR-011.

### BR-005: Re-target within existing folders only
A re-targeted Target Location must still be an existing folder beneath a Routing Root, never fabricated — enforces the TARGET_LOCATION invariant (entity_model TARGET_LOCATION) and C-003.

### BR-006: Surface carries no routing logic
The Action Plan is a thin adapter over the UI-agnostic Proposal contract; reviewing/deciding adds no routing or approval logic to the surface — enforces the "Approval Surface not modeled as data / no logic in surface" decision (entity_model *Terms intentionally not modeled*) and C-009 / ADR-0002.
