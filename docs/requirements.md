# Requirements — M2 · Attachment Auto-Router

Source: [vision.md](vision.md). Stable function/capability/pain IDs (`F##`, `M#`, `P##`, `A##`,
`CON-#`) are defined in the [vision](vision.md) and [`../plan/01-foundation.md`](../plan/01-foundation.md).
Each requirement below traces back to a vision element in its title or row.

## Functional Requirements

Define what the system does. All in user-story form.

| ID     | Title                         | User Story                                                                                                                                                                                                                            | Priority | Status   |
| ------ | ----------------------------- | ------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- | -------- | -------- |
| FR-001 | Detect Attachment (F01)       | As a mailbox owner, I want the system to detect mails carrying at least one attachment worth filing so that I do not have to scan my inbox manually.                                                                                  | Medium   | Open     |
| FR-002 | Extract Attachment (F02)      | As a mailbox owner, I want the system to extract the file object from each detected mail so that it can be processed without a manual download.                                                                                       | High     | Open     |
| FR-003 | Classify Attachment (F03)     | *Deferred to M2b.* v1 routes by **Sender only**; document-type classification (the closed-but-editable enum invoice / contract / … / `other`) and its type-confidence move to the M2b intelligent router.                             | —        | Deferred |
| FR-004 | Derive Target Location (F04)  | As a mailbox owner, I want the system to map each attachment via its Routing Key (Sender = From email address × document type) to an existing folder beneath the declared Routing Roots so that I do not decide where each file goes. | High     | Open     |
| FR-005 | Route Uncertain to Staging    | As a mailbox owner, I want attachments with unknown mappings or low confidence routed to a `_review` staging area so that nothing is filed into the wrong place.                                                                      | High     | Open     |
| FR-006 | Present Proposal for Review   | As a mailbox owner, I want all proposed filing actions presented together as an editable Action Plan with full context so that I can decide without opening the original mail.                                                        | High     | Open     |
| FR-007 | Approve, Edit, or Reject      | As a mailbox owner, I want to approve, edit, or reject each proposal so that I stay in control of what gets filed.                                                                                                                    | High     | Open     |
| FR-008 | Commit Approved File (F22)    | As a mailbox owner, I want each approved attachment copied into its Target Location under its Target Filename when I run `apply` so that only approved rows are committed.                                                              | High     | Open     |
| FR-009 | Record Provenance (F06)       | As a mailbox owner, I want every filed copy linked to its source mail (Message-ID, date, sender) via the external Provenance Ledger so that I can trace any document to its origin.                                                   | High     | Open     |
| FR-010 | Bidirectional Findability     | As a mailbox owner, I want to locate a filed copy from both its Target Location and the source Mail so that nothing is lost in the filing process.                                                                      | Medium   | Open     |
| FR-011 | Manual Rename                 | As a mailbox owner, I want to edit the Target Filename of any proposal in the Action Plan before `apply` so that files land under a name I choose. (AI-suggested naming is M2b/F32.)                                                  | High     | Open     |
| FR-012 | Deduplicate Identical Content | As a mailbox owner, I want identical bytes (same content-hash) never filed twice — only a new provenance link recorded — so that re-sent or re-scanned attachments do not create duplicates.                                          | High     | Open     |
| FR-013 | Flag Conflict                 | As a mailbox owner, I want a same-path/different-content collision flagged in the Action Plan for me to resolve (rename / overwrite / skip) so that nothing is silently overwritten.                                                  | High     | Open     |
| FR-014 | Select Run Scope              | As a mailbox owner, I want to choose which mails a run processes (a folder + optional date range) so that I control the batch; re-scanning overlapping mail is safe (dedup).                                                          | Medium   | Open     |

## Non-Functional Requirements

Measurable quality attributes. Each is testable with a pass/fail threshold.

| ID      | Title                 | Requirement                                                                                                                                                                                                                                                                                                                         | Category        | Priority | Status |
| ------- | --------------------- | ----------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- | --------------- | -------- | ------ |
| NFR-001 | Confidence Gate       | F03 emits a type-confidence and F04 a location-confidence (both in [0,1]); the gate compares **min(type, location)** to the configured threshold; below it the item routes to `_review/`, with 0 auto-approvals below threshold.                                                                                                    | Usability       | High     | Open   |
| NFR-002 | Idempotency           | Re-running the pipeline against already-processed mail must produce 0 duplicate writes; the **dedup decision keys on content-hash** (provenance links keyed on `(Message-ID, content-hash)`), stored in the external Provenance Ledger. Re-running against **staged-but-unfiled** Attachments likewise produces 0 duplicate staged files — staging is content-hash-addressed, so a re-run overwrites identical bytes harmlessly (C-015).                                                                          | Maintainability | High     | Open   |
| NFR-003 | Proposal Completeness | 100% of proposals must display all M2 v1 fields — sender, Target Location, and the location-confidence score — before the approval step. (Document type and type-confidence join in M2b per ADR-0003, making it five fields then.)                                                                                                  | Usability       | High     | Open   |
| NFR-004 | Inclusion Bias        | F01 must surface 100% of ambiguous attachments (e.g. generic names like `scan.jpg`) for review; 0 ambiguous attachments may be silently dropped.                                                                                                                                                                                    | Usability       | High     | Open   |
| NFR-005 | Provenance Coverage   | 100% of filed copies must be resolvable from both their Target Location and their source Mail via the external Provenance Ledger, without any write-back to the mailbox — and must stay resolvable even after the user relocates the source mail within the mailbox (lookups key on `Message-ID`, never on folder location). | Usability       | Medium   | Open   |
| NFR-006 | Credential Containment | 0 mail-access credentials (IMAP password, OAuth/refresh token, Graph client secret) may appear in any M2-produced artifact — Provenance Ledger, Action Plan / plan file, per-copy provenance back-link, or application logs; credentials are read at run time from an OS-level secret store. See ADR-0005, C-011.                                | Security        | High     | Open   |
| NFR-007 | Ledger Siting          | The Provenance Ledger (a PII-bearing sender→filed-location index) must be sited outside any cloud-synced or shared path: 0 ledger instances may resolve to a path beneath a known sync/share root. The use-case spec fixes the concrete location; this NFR is its pass/fail check. See C-012, ADR-0001.                                           | Security        | High     | Open   |
| NFR-008 | Run Outcome Summary    | Every run must emit a per-run outcome tally — counts of **filed / staged / conflicted / errored** Attachments — surfaced to the User in the Action Plan, and the four counts must sum to 100% of the Attachments the run began processing (the testable form of the no-silent-drop guarantee, C-014). Richer structured logging/metrics are deferred (see Postponed decisions).                                                                                                  | Observability   | Medium   | Open   |

## Constraints

Boundaries imposed on the solution.

| ID    | Title                               | Constraint                                                                                                                                                                                                                                             | Category    | Priority | Status   |
| ----- | ----------------------------------- | ------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------ | ----------- | -------- | -------- |
| C-001 | Non-Destructive (CON-1)             | The system must file a copy only; it must never move, delete, or modify the source mail or attachment.                                                                                                                                                 | Technical   | High     | Open     |
| C-002 | Human-in-the-Loop (CON-2)           | No attachment may be written to the Target Location without an explicit approval step, following the HumanLayer `require_approval` light-approval pattern (pattern only, not the deprecated SDK); realised as the plan/apply Action Plan (ADR-0002).     | Operational | High     | Open     |
| C-003 | Existing Folders Only (CON-4)       | F04 must select from the existing folders beneath the declared Routing Roots and must never fabricate a folder path; folder creation is out of scope for v1.                                                                                           | Technical   | High     | Open     |
| C-004 | Private Mailbox Only (v1)           | v1 must target the private mailbox only; acontis, shared, and PST mailboxes are excluded from scope.                                                                                                                                                   | Business    | High     | Open     |
| C-005 | Pareto / Spare-Time (CON-3)         | Scope must stay limited to relief of pains P01 and P02; every design decision must prefer the simplest surface that works over added capability.                                                                                                       | Business    | High     | Open     |
| C-006 | Stack TBD (CON-7)                   | Programming language and runtime are not fixed here; the choice is deferred to the build-spine plan step.                                                                                                                                              | Technical   | Medium   | Deferred |
| C-007 | Mail-Access Method TBD (CON-8)      | The mail-access method (IMAP / Graph / PST / Outlook / Kerio) is deferred to the use-case spec — now unblocked, as idempotency keys on content-hash + portable `Message-ID`, not a transport id. (Approval surface and Run Scope are resolved, below.) | Technical   | Medium   | Deferred |
| C-008 | External Provenance Ledger (CON-11) | Bidirectional findability must be served by an external ledger (also the dedup store), never by annotating the source mail (CON-1). See ADR-0001.                                                                                                      | Technical   | High     | Open     |
| C-009 | Surface/Core Separation (CON-12)    | No routing or approval logic may live in an Approval Surface; the Proposal is a UI-agnostic contract and every surface (plan/apply now, GUI later) is a thin adapter. See ADR-0002.                                                                    | Technical   | High     | Open     |
| C-010 | Dedup vs Conflict                   | Identical content (same content-hash) is silently de-duplicated; only same-path/different-content is a Conflict surfaced to the User. The two must not be conflated.                                                                                   | Technical   | High     | Open     |
| C-011 | Credential Siting                   | Mail-access credentials live only in an OS-level secret store, read at run time, and must never be written into the Provenance Ledger, the Action Plan / plan files, the provenance back-link, or logs. The principle is fixed now; the concrete store/flow rides with the C-007 access-method choice in the use-case spec. See ADR-0005, NFR-006. | Security    | High     | Open     |
| C-012 | PII-Bearing Ledger (Owner-Private)  | The Provenance Ledger and the provenance back-link are PII-bearing and owner-private: they hold personal data (Sender address, mail date, content fingerprint, filed-copy location). The ledger must be sited outside cloud-synced/shared paths (NFR-007); the back-link carries only origin fields (Message-ID, date, Sender) and is never widened with further personal data. See ADR-0001. | Security    | High     | Open     |
| C-013 | Data Retention Stance (v1)          | The three accumulating artifacts have a fixed v1 retention stance: (a) the **Staging Area** (`_review/`) is **manually managed by the User** — M2 never auto-deletes from it and applies no TTL; (b) per-run **Action Plans** are **retained** as the plan/apply audit trail (no rotation/purge); (c) the **Provenance Ledger** is **append-only and never purged** in v1. M2 implements no automated retention, TTL, or garbage-collection — that mechanism is deferred (see Postponed decisions).                                                                  | Operational | Medium   | Open     |
| C-014 | No Silent Drop (Terminal Outcome)   | Every Attachment the pipeline begins processing must reach **exactly one** terminal outcome — **filed / staged / conflicted / errored** — and must never be silently dropped. An Attachment that cannot be hashed, parsed, or copied routes to the **Staging Area** as an explicit *errored* outcome and is surfaced in the Action Plan, even when no routable Proposal can be formed. The per-run tally of the four outcomes is NFR-008.                                                                                  | Operational | High     | Open     |
| C-015 | Concurrency Stance (v1: Single-Writer + Idempotent Staging) | M2 v1 assumes **single-writer** runs: exactly one pipeline run writes the Provenance Ledger and the Staging Area at a time. There is no run serialization or file-locking, so overlapping runs (e.g. a scheduled run colliding with a manual one) are **unsupported** in v1 — the User must not run two pipelines concurrently. Staging is **idempotent**: a staged-but-unfiled Attachment is written into `_review/` at a content-hash-addressed path, so a re-run overwrites identical bytes harmlessly (0 duplicate staged files, NFR-002); the Attachment is **re-proposed each run** until the User drains `_review/` (interacts with the C-013 `_review/` retention stance). Real file-locking / concurrent-run support is deferred (see Postponed decisions). | Operational | Medium   | Open     |

## Open Questions

- **NFR-001 threshold value** — the `min(type, location)` confidence cutoff that routes items to
  `_review/` is not fixed. Set it **empirically against the golden corpus** (e.g. ~0.7), not by guess.
- **C-007 / mail-access method** — IMAP vs Graph vs PST vs Outlook vs Kerio is still deferred, but
  **no longer blocks anything**: NFR-002's dedup key is content-hash and the provenance key uses the
  portable `Message-ID`. The choice can be made at the use-case spec / build step on its own merits.

## Scope split (against M2 · Attachment Auto-Router)

### In scope
- FR-001, FR-002, FR-004 — detect / extract / derive-target (Sender-only): M2 substrate F01/F02/F04.
- FR-005–FR-014 — staging, Action Plan, approve/edit/reject, commit, provenance, findability, manual rename, dedup, conflict, run-scope: the M2 plan/apply loop for pains P01/P02.
- NFR-001–NFR-008 — confidence gate, idempotency, proposal completeness, inclusion bias, provenance coverage, credential containment, ledger siting, run-outcome summary: M2 quality thresholds.
- C-001–C-005, C-008, C-009, C-010, C-011, C-012, C-013, C-014, C-015 — non-destructive, HITL, existing-folders-only, private-mailbox-only, Pareto, provenance ledger, surface/core separation (ADR-0002), dedup-vs-conflict, credential siting (ADR-0005), PII-bearing ledger, data-retention stance, no-silent-drop outcome, concurrency stance (single-writer + idempotent staging): M2 boundaries.

### Deferred
- FR-003 Classify Attachment (F03) — document-type classification and type-confidence; M2 v1 routes by Sender only, so a second routing signal is not needed at this marker.

## Postponed decisions
- [FR-003 Classify Attachment (F03)] Deferred: document-type classification (invoice/contract/…/`other` enum) and its type-confidence. Reason: M2 v1 routes by Sender only; a second routing signal is not needed at this marker (G1/G10). Revisit when: M2 ships and M2b (Intelligent Auto-Router) begins.
- [C-006 Stack TBD] Deferred (pre-existing — see C-006): programming language/runtime choice. Reason: no concrete requirement at M2 fixes the stack (G3). Revisit when: the build-spine / use-case-spec step is reached.
- [C-007 Mail-Access Method TBD] Deferred (pre-existing — see C-007): IMAP/Graph/PST/Outlook/Kerio choice. Reason: idempotency keys on content-hash + portable `Message-ID`, so no M2 requirement forces it (G3). Revisit when: the use-case-spec / build step is reached.
- [C-013 Automated retention / GC] Deferred: any automated retention mechanism — `_review/` draining or TTL, Action-Plan rotation/garbage-collection, ledger purge/compaction. Reason: M2 v1 fixes only the *stance* (manual `_review/`, retained plans, append-only never-purged ledger — C-013); the behaviour is already correct without a mechanism, and unbounded growth is acceptable at single-user M2 scale (G1/G3, hidden-constraint sweep Gap 3). Revisit when: `_review/` or the ledger grows large enough to need lifecycle management, or a later iteration adds it as an NFR.
- [NFR-008 Rich run metrics / structured logging] Deferred: structured/queryable run logs, per-Sender or time-series metrics, dashboards, and any machine-consumable telemetry beyond the plain per-run filed/staged/conflicted/errored tally. Reason: M2 v1 fixes only the *trust* layer — the no-silent-drop guarantee (C-014) and its simple outcome tally surfaced in the Action Plan (NFR-008) — which is enough for a single-user pipeline; richer observability is a mechanism, not a correctness property (hidden-constraint sweep Gap 5). Revisit when: a later iteration or operability need (e.g. unattended scheduling, multi-mailbox) makes the plain tally insufficient.
- [C-015 Concurrent-run support / file-locking] Deferred: real file-locking, run serialization, lock files, or any concurrent-run support. Reason: M2 v1 fixes only the single-writer *stance* (one run at a time — C-015) plus idempotent content-hash-addressed staging; behaviour is correct at single-user scale without a locking mechanism, and the User simply does not run overlapping pipelines (G1/G3, hidden-constraint sweep Gap 7). Revisit when: scheduled/unattended runs can overlap a manual run, or multi-mailbox/concurrent operation is added.
